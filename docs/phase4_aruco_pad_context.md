# Context hand-off: Phase 4 — ArUco landing pad perception

For the Claude agent working on the Raspberry Pi. This summarises a planning/diagnosis session
held on the team's laptop (2026-11-20/21). Read it before working on vision, the landing pad
or the flight-test workflow. Verify file contents before relying on them: the laptop copy and
the Pi copy of the repo have diverged before.

## 1. Project and hardware

- F450 quadcopter, Pixhawk 1 running **ArduPilot ArduCopter 4.7.2** (not PX4, despite older docs).
- Raspberry Pi 5 runs `src/main.py`: camera (USB `usb_0bdc_8088`, **640x360 @ 30 fps**, MJPG),
  VL53L1X rangefinder (I2C), MAVLink to the Pixhawk over CP2102 USB-serial at 921600 (TELEM2).
- Goal: land on an ArUco landing pad, finally on an **oscillating platform**.
- Camera calibration: `src/inputs/camera_driver/calib/usb_0bdc_8088_640x360.yaml`
  (fx 654.1, fy 654.7, cx 326.1, cy 160.2, rms 0.33 px, FOV 52.1° x 30.8°).
  Note: fx std dev 12.7 px (~1.9 %) → up to ~2 % scale uncertainty until validated with a tape.

## 3. Physical landing mat (built, being glued)

- 30 x 30 in (**762 x 762 mm**) corrugated plastic, A4 tiles glued with spray adhesive.
- Generated by **`tests/vision/make_pad.py`** from the **`landing_pad`** section of
  **`src/inputs/camera_driver/config.yaml`** (single source of truth for print and code).
  Outputs in `tests/vision/markers/`: `pad_tiles.pdf` (12 tiles, speckle background for optical
  flow), `pad_markers.pdf` (markers cut out and glued into outlined boxes), `pad_preview.png`.
- Speckle background exists because the **flow uses the same camera**; a plain mat kills flow
  quality right over the pad. Density was halved at the user's request (still 75/75 flow features
  at 0.5–1 m in simulation; do not reduce further).

Pad frame (seen from above, mm): **origin = where the drone centre touches down (mat centre),
x = right, y = FRONT (landing heading), z = up**. Every marker glued with its printed top edge
towards FRONT. Dictionary `DICT_4X4_50`.

| ID | Size (design) | Centre (mm) | Role | Working range |
|---|---|---|---|---|
| 20 | 25 mm, margin 10 | (0, 0) | Touchdown; must be under the **camera** at landing | 0.09–0.6 m |
| 10 | 100 mm, margin 17 | (−100, 0) | Main approach marker | ~0.33–2.5 m |
| 31–34 | 50 mm, margin 10 | (±280, ±280) | Steadier pose, backup vs glare / off-centre | ~0.3–1.3 m |

Design decisions already made (do not revisit without reason):
- **No same-ID nesting** (two ID 10s of different sizes give 4x distance errors; the tracker is keyed
  by ID). **No marker inside another**: ID 10's centre 2x2 cells are black and `DICT_4X4_50`
  corrects only 1 bit. Side-by-side layout instead.
- Big/small handover overlap is 0.33–0.6 m (both visible).
- `camera_offset_mm: [0, 0]` is a **placeholder** — the real camera offset from the drone centre
  has not been measured. If non-zero, ID 20 must move to that point (and ID 10 100 mm to its left).
- The designed values in `landing_pad` must be replaced with **measured** values after gluing
  (calipers ±0.2 mm for sizes, ruler ±1 mm for centres). They define the 3D model used by the pose
  solver; they are not a z-calibration. Size error → scale error in height and x/y; position error →
  origin offset and jumps at marker handover.

## 4. Current task: single-marker validation (ID 10 on the floor)

Tool: `tests/vision/aruco_live.py` (web view at `http://<pi-ip>:8000/`, key `m` = 1 s average
appended to `tests/vision/measurements.csv`, `r` = record frames for offline replay).

Run with the onboard config so only ID 10 is accepted (the default `tests/camera/config.yaml`
accepts IDs 10, 25, 32 — the mat's ID 32 would be read as 100 mm):

```bash
sudo systemctl stop uav-opl   # the onboard main.py service — only one program can open the camera
python3 tests/vision/aruco_live.py --config src/inputs/camera_driver/config.yaml
```

Known bug (fixed on laptop, may be missing on the Pi): `tests/camera/cameras/factory.py` passed the
onboard-only key `nominal_focal_px` to the camera backend → `unexpected keyword argument`.
Fix = filter `NON_BACKEND_KEYS = ("nominal_focal_px",)` exactly like
`src/inputs/camera_driver/cameras/factory.py` does.

Before testing: put the **caliper-measured** ID 10 size in `aruco.marker_mm` of the onboard config.

Tests (camera stays on the drone, pointing straight down, tape height = floor → lens front):
- **A** height series, marker centred: 0.30, 0.50, 0.75, 1.00, 1.25, 1.50, 2.00 m, `m` x3 each;
  fill `true_distance_m` and `notes` in the CSV.
- **B** image edges at 1.00 m (left/right/top/bottom): z should stay ~1.00.
- **C** steadiness at 1.00 m: `m` x5.
- **D** range limits (min ~0.25 m expected, max ~2.5 m at ~26 px).
- **E** axis directions: nose towards mat FRONT, slide drone 10 cm forward then right; record
  which of x/y changes and its sign (needed for camera→body rotation).

Pass: z error ≤ 1 % (0.3–1.5 m), ≤ 2 % at 2 m; std < 3 mm at 1 m; edges within 1–2 cm of centre;
reprojection error < 0.5 px.
Interpretation: same % error at all heights → scale (marker size or focal length, recalibrate with
more tilted views); same mm offset → reference point (lens front vs optical centre, harmless);
worse at edges → distortion calibration.

## 5. Next: whole-board ("pad") pose integration — planned steps

Existing code to build on: `src/logic/vision/aruco_detector.py` (edge-refined corners),
`pose.py` (IPPE_SQUARE, marker frame x right / y up / z out), `tracker.py` (per-ID smoothing,
hold), `measurement.py`, `tests/vision/test_pose.py` + `synthetic.py`.

1. **Measure the mat → config** (user).
2. **Pad model**: from `landing_pad`, 3D corners per marker (metres, z = 0, order TL, TR, BR, BL
   with marker top = +y) → `cv2.aruco.Board`; detector restricted to pad IDs (10, 20, 31–34).
3. **Pad pose solver**: all visible pad corners in one PnP solve (≥ 2 markers); single marker →
   IPPE_SQUARE then shift by its pad position. Per-marker residuals; drop outlier marker and
   re-solve. Output: camera position in pad frame (x, y, height), pad yaw, IDs used, error; keep
   pad origin in camera frame in the existing `x, y, z` fields for ground-station compatibility.
4. **Offline synthetic test**: render the assembled mat (`make_pad.py` raster) through the real
   calibration at known poses (0.12–2 m, offsets, tilts, yaw). Gate: error ≤ max(5 mm, 1 % of
   height); **no jump > 1 cm** while descending through the ID 10 → ID 20 handover.
5. **Bench with real mat**: `aruco_live.py --pad` mode (to be added): height series, slow descent
   0.8 → 0.15 m recorded, 20 cm slides, board vs single-marker noise, per-marker residual
   self-check (a consistently high marker = re-measure it).
6. **Camera → body → level frame**: fixed rotation from test E + camera offset; **tilt correction
   with Pixhawk roll/pitch at frame capture time** (needs a short ATTITUDE history buffer in
   `VehicleState`, which only stores the latest packet). Gate: tilting ±15° in place moves the
   corrected position < 2 cm. Reason: at 1 m a 10° tilt shifts the raw marker position ~17 cm —
   the same rotation problem the optical flow had.
7. **Onboard integration**: config switch `vision.mode: pad | single`; wire into
   `src/inputs/camera_driver/camera_node.py` → `VisionState` → Wi-Fi telemetry → ground-station
   panel; **onboard per-frame CSV on the Pi** (frame stamp, raw + tilt-corrected pad pose, IDs,
   errors, attitude used, lidar, flow quality, mode, EKF position) — the ground-station flight CSV
   does not record vision at all. Check the camera loop keeps 30 fps with ArUco + flow
   (`proc_ms` < ~15 ms); ArUco must not slow the flow.
8. **Phase 4 observation flights** (after Phase 3 LOITER gate): hovers at 0.5/1/1.5/2 m, slow
   passes, slow descent 1 → 0.3 m. Checks: detection > 90 % at 0.3–2 m, pad height vs lidar
   within 3 %, pad position in world frame steady (std < 3–5 cm), smooth handover, latency
   (for `PLND_LAG`).
9. **Phase 5**: send raw body-frame angles to the **pad origin** as `LANDING_TARGET`; let
   ArduPilot do its own tilt compensation (do not compensate twice).

## 6. Known issues and constraints (important)

- **Pi undervoltage**: `vcgencmd get_throttled` = `0x50005`, `EXT5V_V` = 4.76 V on the ground,
  `usb_max_current_enable=0`. Likely cause of in-flight telemetry freezes (the Pi kept streaming
  but its Pixhawk data stopped updating → CP2102 USB link dropped, taking the rangefinder and
  flow with it). **No flights until `0x0`** (≥ 5 A BEC at 5.1–5.2 V, short thick wires; only then
  `usb_max_current_enable=1`). Also degrades vision fps (CPU throttled).
- **Mechanical yaw imbalance**: M1+M2 ~390 µs above M3+M4 in hover (also in STABILIZE), ~11° yaw
  kick at take-off.
- **`debug_force_arm()`** permanently writes `ARMING_CHECK`, `DISARM_DELAY`, `BRD_SAFETYENABLE`,
  `FS_THR_ENABLE` = 0. **The user explicitly wants it kept as is — do not modify it.** Instead run
  `flowcheck` before every real flight to catch `FS_THR_ENABLE=0`.
- **Optical flow sign**: the Pi's `sensor_feed.py` sends raw camera flow with `FLOW_SIGN_X/Y = 1`.
  By ArduPilot's convention (pure rotation → flowRate ≈ gyro; moving right → +flow_rate_x;
  moving forward → −flow_rate_y) and the 2026-11-20 hand tests (forward → +rad_y, right → −rad_x),
  both axes may be inverted. `flowtest` must confirm signs before any LOITER flight.
- **MAVLink 2** is not forced; `flow_rate_x/y` are MAVLink2 extension fields. pymavlink auto-switches
  on the first v2 frame from the Pixhawk; confirm `OPTICAL_FLOW` quality > 0 in QGC (System 1).
- Run only **one ground station** at a time (the Pi retargets telemetry to whichever laptop
  handshakes last).
- Mat: matte only, no glossy tape/laminate over markers (glare kills detection).
